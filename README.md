# Sensor Image Classification

Курсовий проєкт: класифікація сенсорних сигналів за зображеннями
осцилограм методами машинного навчання.

Класи:
- `acetone`  — ацетон
- `ammonia`  — аміак
- `ethanol`  — етанол
- `RH`       — відносна вологість (контрольний/фоновий клас)

## Що робить програма

```
PNG-зображення осцилограми
        │
        ▼
  обрізання інтерфейсу осцилографа
        │
        ▼
  виділення жовтої кривої (HSV-маска)
        │
        ▼
  перетворення маски у 1D-сигнал (медіана y по стовпцях)
        │
        ▼
  згладжування + інтерполяція пропусків
        │
        ▼
  пошук імпульсів (find_peaks → fallback на 3 рівні частини)
        │
        ▼
  контроль якості імпульсу (амплітуда, ширина, шум, покриття)
        │
        ▼
  числові ознаки (амплітуда, площа, rise/fall time, енергія, ...)
        │
        ▼
  ML-моделі (LR, KNN, SVM, DT, RF, GBM)  +  опційно CNN
        │
        ▼
  голосування прогнозів імпульсів → фінальний клас + впевненість
```

## Дві гілки дослідження

Проєкт розділений на дві **незалежні** гілки, які можна запускати окремо
і паралельно:

| Гілка | Вхід | Методи |
|---|---|---|
| **image** | готові картинки вирізаних імпульсів (PNG) | ablation представлення входу, HOG + SVM/LogReg/RF/XGBoost, MobileNetV2 (frozen) + класичні голови, 2D-CNN |
| **features** | 35 числових ознак на імпульс | GroupKFold по 7 моделях, decision-level fusion, PCA/LDA |

```bash
python run_experiments.py --branch image      # лише картинки
python run_experiments.py --branch features   # лише ознаки
python run_experiments.py --branch both       # обидві ОДНОЧАСНО (окремі процеси)
python run_experiments.py --summary           # зведена таблиця без обчислень
```

Те саме у браузері — сторінка **`/experiments`**: дві кнопки, два
прогрес-бари, зведені таблиці й монтажі візуального контролю входу.

**Чому окремі процеси, а не потоки:** TensorFlow і sklearn обидва
захоплюють CPU-пул, а GIL заважав би ще й на рівні Python. Логи гілок —
`results/logs/branch_<name>.log`.

### Представлення входу image-гілки (Група 0)

Основний формат — `letterbox_gray-mask_192x96` (`src/image_prep.SPEC_MAIN`).
Вибраний не з міркувань, а за ablation-експериментом: пробник
HOG + SVM на всіх специфікаціях, image-level f1 (OOF, GroupKFold 5),
`results/image_input_ablation.csv`.

| Представлення | HOG-ознак | image f1 | Δ до baseline |
|---|---|---|---|
| letterbox gray+mask **256×128** | 7560 | **0.9004** | +0.0083 |
| letterbox gray+mask **192×96** | 3960 | 0.8988 | +0.0067 |
| **stretch gray 96×96** (baseline) | 900 | 0.8921 | — |
| letterbox gray+mask 128×128 | 3528 | 0.8781 | −0.0140 |
| letterbox rgb 96×96 | 2700 | 0.8774 | −0.0147 |
| letterbox gray+mask 96×96 | 1800 | 0.8727 | −0.0194 |
| letterbox mask 96×96 | 900 | 0.8650 | −0.0271 |
| letterbox gray 96×96 | 900 | 0.8592 | −0.0329 |

Що з цього випливає:

- **letterbox сам по собі НЕ допомагає.** При однаковому розмірі 96×96 і
  однаковій розмірності дескриптора (900) `letterbox_gray` **гірший** за
  `stretch_gray` на 0.0329. Причина видно на дампі: імпульс має пропорцію
  ~1:1.93, тож letterbox у квадрат вкладає криву в 50×96 і віддає ~48%
  кадру під чорний паддинг — втрата роздільності переважує виграш від
  незіпсованої геометрії.
- **Виграє letterbox лише разом із некватратним розміром.** Чесне
  порівняння при близькій розмірності: 192×96 (3960 ознак, 0.8988) проти
  128×128 (3528 ознак, 0.8781) — **+0.0207** на користь пропорції 2:1.
- **gray + HSV-маска двома каналами.** Маска глушить сітку осцилографа,
  канал grayscale зберігає шумову смугу навколо кривої. Маска поодинці —
  найгірший з інформативних каналів (0.8650): поріг `V>=80` відсікає
  розмиту смугу, а це фактично `amp_to_noise` — одна з найсильніших ознак
  сигнальної гілки.
- **Чому 192×96, а не 256×128.** Різниця 0.0016 при вчетверо довшому
  прогоні (60.9 с проти 22.3 с) і в межах std фолдів (0.013–0.019).

**Застереження про конфаунд:** кількість HOG-ознак змінюється від 900 до
7560 разом із розміром входу, тож частина різниці між рядками різного
розміру — це ємність дескриптора, а не якість представлення. Вільні від
конфаунду порівняння — всередині 96×96 і 192×96 vs 128×128; саме на них
спираються висновки вище.

Перевірити очима:

```bash
python -m src.image_prep     # дамп у processed/image_prep_debug/
```

Для кожної специфікації: `montage.png` (рядок = клас) і по зразках
`0_original` → `1_mask` → `2_input` → `3_input_x6` → `4_side_by_side`.

### Аугментація зображень: чому без фліпів

Стандартний `horizontal_flip` / `vertical_flip` тут **заборонений**:
перший обертає час (міняє місцями фронт і спад), другий інвертує
амплітуду. Обидва руйнують саме ті ознаки, за якими розрізняються класи.
Лишаються зсуви, zoom ±10% і контраст (`src/image_methods.build_cnn2d`).

### Нормалізація 2D-CNN: чому GroupNorm, а не BatchNorm

Перший прогін CNN на правильному вході дав f1 **0.1135** — нижче
випадкового (~0.25). Дані з підозр виключились одразу: HOG на ТИХ САМИХ
масивах давав 0.87. Вирішальний тест — точність на **тренувальних** даних
у режимі inference:

| Нормалізація | train (inference) | val | test |
|---|---|---|---|
| BatchNorm momentum=0.99 | **0.2269** | 0.2326 | 0.2184 |
| BatchNorm momentum=0.85 | 0.7211 | 0.6589 | 0.6893 |
| **GroupNorm (=LayerNorm)** | **0.9942** | 0.8992 | 0.8981 |
| без нормалізації | 0.8772 | 0.8062 | 0.8252 |

Модель із train-accuracy 0.9986 у режимі навчання давала 0.2269 на тих
самих даних у режимі inference — отже мережа навчилась, а ламав її
перехід із батчевих статистик на ковзні: вхід розріджений (≈97% пікселів
— чорне тло, mean 0.03), кроків на епоху мало (~22), і ковзні середні BN
не встигають за зсувом розподілу активацій.

`GroupNormalization(groups=-1)` нормалізує кожен зразок окремо — розриву
train/inference не існує в принципі. Результат: **0.1135 → 0.9187**.
Перемикач `norm` у `build_cnn2d()` приймає `groupnorm` (типово),
`batchnorm`, `none` — щоб відтворити таблицю вище.

### Єдина таблиця всіх моделей

Гілкові CSV мають різні схеми, а image-level у гілці ознак раніше
рахувався лише для однієї моделі — тож «SVM на ознаках проти SVM на
картинках» порівняти було нічим. `src/compare_all.py` зводить **усі**
моделі обох гілок в один файл `results/all_models_comparison.csv` під
одним протоколом (GroupKFold(5) за `source_image`, OOF, злиття на знімок):

```bash
python -m src.compare_all                 # 2D-CNN береться з кешу (швидко)
python -m src.compare_all --with-cnn      # перерахувати і його (~25 хв)
python run_experiments.py --compare-all
```

Колонки однакові для кожного рядка:

| Колонка | Що це |
|---|---|
| `pulse_f1` | рішення по окремому імпульсу (OOF) |
| `image_f1_majority` / `_mean_proba` / `_weighted` | те саме рішення, злите на знімок трьома стратегіями |
| `image_f1_best`, `best_strategy` | найкраща з трьох (при рівності перевага `weighted`) |
| `params_key`, `params_full` | фактичні гіперпараметри рядка — таблиця самодостатня, лізти в код не треба |
| `source` | `computed` або `cached`, якщо рядок узятий із попереднього прогону |

Три стратегії злиття рахуються з тих самих OOF-ймовірностей, тому
коштують нуль додаткового навчання (`evaluate_oof(..., all_strategies=True)`).

У браузері — кнопка «Порахувати таблицю» на сторінці `/experiments`.

Що видно лише з повної таблиці:

1. **Верхівка нерозрізненна.** П'ять перших моделей лежать у смузі
   0.9206–0.9233 — це 0.0027 при std фолдів 0.016–0.025. Стверджувати,
   що XGBoost «кращий» за MobileNetV2 + LogReg, немає підстав; коректне
   формулювання — обидві парадигми виходять на стелю ~0.92.
2. **Порядок на рівні імпульсу інший, ніж на рівні знімка.** Найкращий
   pulse f1 у 2D-CNN (0.8960), але після злиття він шостий; features +
   XGBoost із гіршим pulse (0.8918) дає найкращий image. Ранжувати
   моделі за pulse-метрикою — помилка: злиття перерозподіляє місця.
3. **Оптимальна стратегія злиття залежить від моделі.** `weighted`
   виграє у 8 моделей, `mean_proba` — у 7, `majority` не виграє ніде
   (він викидає інформацію про впевненість). Тобто «weighted завжди
   краще» з Фази 2 — надто сильне твердження; вірно лише в середньому.
4. **Різниця може бути в гіперпараметрах, а не в підході.** SVM на
   ознаках дає 0.8421, SVM на HOG — 0.9016, але в першої `C=1.0`, у
   другої `C=10.0` (див. `params_key`). Це різні моделі, і рядки не
   можна читати як «картинки кращі за ознаки для SVM».

#### Чому SVM має різні числа в різних таблицях

`features_branch_results.csv` дає SVM pulse-f1 **0.7915**, а
`all_models_comparison.csv` — **0.8320**. Це не помилка і не різні
спліти: перша таблиця міряє `model.predict()`, друга —
`argmax(model.predict_proba())`, бо для злиття на знімок потрібні саме
ймовірності. Для `SVC(probability=True)` це різні правила рішення:
ймовірності дає Платтове калібрування, навчене окремою внутрішньою
крос-валідацією, і воно може не збігатися з гіперплощиною.

Перевірено прямим заміром на тому самому протоколі:

| Модель | `predict` | `predict_proba` | Δ |
|---|---|---|---|
| **SVM** | 0.7915 | 0.8313 | **+0.0398** |
| LogisticRegression | 0.8387 | 0.8387 | 0.0000 |
| RandomForest | 0.8885 | 0.8885 | 0.0000 |

Тобто розходиться лише SVM, і саме через калібрування. Усередині
`all_models_comparison.csv` усі моделі міряються однаково
(`predict_proba`), тож таблиця самоузгоджена — але порівнювати її рядок
SVM із рядком SVM зі старої гілкової таблиці не можна.

### Порівняння гілок

`results/branch_comparison.csv`:

| Гілка | Найкращий метод | Вхід | image f1 |
|---|---|---|---|
| image | MobileNetV2 frozen + LogReg | 192×96, gray+mask | **0.9211** |
| features | RandomForest + weighted fusion | 35 числових ознак | 0.9210 |

**Гілки зрівнялися.** Попередня зведена таблиця роботи давала «чітку
ієрархію» — ознаки (0.921) > гібрид (0.91) > 1D-CNN (0.846) > 2D-CNN
(0.814) — і висновок, що рендеринг сигналу в 2D-картинку є найгіршою
стратегією. Після виправлення входу (Група 0) і нормалізації (GroupNorm)
2D-CNN дає 0.9187, а MobileNetV2 frozen + LogReg — 0.9211. Тобто
попередній розрив був артефактом двох технічних дефектів, а не
властивістю даних.

Що лишається в силі:

- **decision-level fusion** дає найбільший приріст і в image-гілці теж
  (pulse 0.87–0.90 → image 0.92);
- **ручні ознаки лишаються найдешевшими**: 0.9210 за ~70 с проти 1449 с
  у 2D-CNN; MobileNetV2 frozen + LogReg — 0.9211 за 1.8 с після
  екстракції ембедингів;
- **межа — в даних**: жоден метод не перетнув ~0.92, головне джерело
  помилок — хімічно близькі acetone↔ethanol.

## Швидкий старт

### 1. Встановити залежності

```bash
python -m venv venv
# Windows: venv\Scripts\activate
# Linux/macOS: source venv/bin/activate

pip install -r requirements.txt
# (опційно для CNN) pip install tensorflow
```

### 2. Покласти зображення в dataset/

```
dataset/PNG-1acetone/001.png, 002.png, ...
dataset/PNG-1ammonia/001.png, 002.png, ...
dataset/PNG-1ethanol/001.png, 002.png, ...
dataset/PNG-1RH/001.png, 002.png, ...
```

Назви файлів типу `001.png`, `002.png` — програма автоматично дістає
з них `file_number` (для acetone/ammonia/ethanol номер відповідає
концентрації; для RH використовується як ID).

### 3. Запустити меню

```bash
python app.py
```

Найшвидший шлях — пункт **8 (повний pipeline)**: він зробить індексацію,

## Як перевірити модель на новому знімку

Обидві гілки тепер мають робочий inference, і шлях до рішення в них
спільний аж до класифікатора:

```
PNG → crop інтерфейсу → HSV-маска → 1D-сигнал → межі імпульсів
    → контроль якості (погані імпульси відкидаються)
    → ┬─ 35 ознак      → ML-модель        (src/predict.py)
      └─ картинка імпульсу → HOG/ембединги → модель (src/predict_image.py)
    → зважене злиття (вага = local_coverage × amp_to_noise)
    → клас + впевненість; < 0.55 → попередження
```

Межі імпульсів і метод сегментації беруться з
`features/pipeline_meta.json`, а картинка вирізається тією самою
`crop_pulse_image`, що й при побудові датасету — інакше inference бачив
би інший кадр, ніж бачило навчання.

Межі імпульсів (`full_cycle`) — від підніжжя одного фронту наростання до
підніжжя наступного. Фронт шукається гістерезисом за рівнем сигналу:
перехід з нижньої третини розмаху (рівні — 10-й і 90-й перцентилі) у
верхню, що тримається ≥ 3% ширини кадру. Шматки до першого і після
останнього фронту — неповні цикли, вони не класифікуються.

На сторінці результату `/predict` внизу є блок **«Як оброблено знімок»**
(`src/predict_trace.py`): рамка обрізання, маска, сирий і згладжений
сигнал, пороги й фронти, межі на знімку і таблиця кожного шматка з
рішенням і причиною — «у модель», «відкинуто» (яке правило контролю якості
не пройдено і з якими числами) або «не імпульс» (край кадру). Для
картинкових моделей показується ще й сам вхід моделі. Трасування викликає
ті самі функції з тими самими аргументами, що й прогноз, тож межі й
рішення збігаються.

```bash
# гілка ознак (models/best_ml_model.pkl)
python -m src.predict dataset/PNG-1acetone/001.png

# картинкові моделі: спершу навчити на всіх даних і зберегти
python -m src.image_model_store
python -m src.predict_image dataset/PNG-1acetone/001.png "HOG + SVM"
```

`image_model_store` пише окремі `models/image_<метод>.pkl` і не чіпає
файли гілки ознак (`best_ml_model.pkl`, `scaler.pkl`, `label_encoder.pkl`,
`best_model_meta.json`). У кожному bundle лежить усе для відтворення
входу: специфікація препроцесингу, параметри HOG, backbone, порядок
класів — щоб inference не міг розійтися з навчанням.

2D-CNN зберігається окремо: joblib-бандл тримає лише метадані, а сама
мережа лежить поруч у рідному форматі `models/image_2d_cnn.keras`
(pickle графа обчислень ненадійний між версіями TensorFlow). Навчання на
повному наборі — один фіт, ~4 хв, валідаційні 15% відрізаються **за
групами**, як і в оцінюванні, інакше рання зупинка орієнтувалась би на
завищену метрику.

```bash
python -m src.image_model_store "2D-CNN"    # лише мережу
python -m src.image_model_store             # усі 8 моделей
```

Архітектура 2D-CNN: 4 блоки Conv2D + GroupNorm + MaxPool, далі
**Flatten** (не GlobalAveragePooling — GAP усереднював карту ознак по
кадру й губив, *де* яка форма; Flatten кращий на кожному з 5 фолдів,
`results/cnn_architecture.csv`). Вхід картинкових моделей —
`letterbox_gray-mask_192x96_clean`: плашка осцилографа «Saved to file …»
зафарбовується (`image_prep.overlay_box_mask`), щоб модель не вчилась на
написі.

**Ансамбль** `Ансамбль: HOG + XGBoost + 2D-CNN` (`image_model_store.ENSEMBLES`)
окремо не навчається: він усереднює ймовірності двох збережених моделей з
рівними вагами. Його CV-метрика в `all_models_comparison.csv` рахується з
OOF-прогнозів учасників (`results/oof/`), без перенавчання. У селекті
`/predict` він з'являється, щойно обидва учасники збережені.

> **Не читайте впевненість на знімках із `dataset/` як якість моделі.**
> `image_model_store` донавчає картинкові моделі на **всьому** наборі —
> стандартна практика для фінальної моделі, але наслідок у тому, що на
> тренувальних знімках вони дають 95–100%. Модель гілки ознак
> (`best_ml_model.pkl`) навчена на train-спліті й на тих самих файлах
> показує 46–74% і подекуди помиляється. Це різниця в тому, що модель
> бачила, а не в тому, що вона вміє. Чесні числа дає лише таблиця
> крос-валідації (`results/all_models_comparison.csv`).

### Хто запам'ятовує, а хто узагальнює

Прямий замір на навчальних даних добре показує різницю в характері
моделей:

| Модель | accuracy на власних навчальних даних | середня впевненість |
|---|---|---|
| HOG + SVM | **1.0000** | 0.95–1.00 |
| 2D-CNN | 0.9017 | 0.821 |

HOG + SVM запам'ятовує набір повністю: `C=10` на 3960 ознаках при 1027
зразках — і його впевнені 95–100% на тренувальних знімках це відтворення
з пам'яті, а не вміння. 2D-CNN на тих самих даних помиляється у ~10%
випадків, бо аугментація, GroupNorm, dropout і рання зупинка не дають їй
вивчити набір напам'ять. Помилки мережі зосереджені там само, де й межа
всього дослідження — acetone ↔ ethanol (49 і 24 випадки).

На крос-валідації обидві дають майже однакове (0.8988 проти 0.9187
image-f1), тобто **тренувальна точність про якість не свідчить взагалі** —
зручна ілюстрація для тексту роботи.

## Ключові методичні рішення

1. **Group train/test split за `source_image`** — імпульси одного
   зображення не потрапляють і в train, і в test. Це уникає
   завищеної точності.
2. **Голосування за імпульсами** — фінальний клас зображення
   формується з усереднених імовірностей якісних імпульсів.
3. **Контроль якості імпульсів** — фільтрація за амплітудою, шириною,
   покриттям маски, рівнем шуму. Погані імпульси виключаються.
4. **Експеримент original vs inverted** (пункт 9 меню) — окремо тренує
   моделі на оригінальних і на інвертованих зображеннях, порівнює
   результати. Це окремий розділ для курсової.
5. **Аналіз концентрації** — для acetone/ammonia/ethanol будується
   залежність ознак від `file_number`. Для RH цей зв'язок не
   передбачається (контрольний клас).
6. **`file_number` не входить в основну модель** — ablation (Фаза 7)
   показав приріст +0.05, але це витік організації датасету, а не
   фізична інформація про речовину.
7. **Спільний протокол оцінювання для всіх методів** — GroupKFold(5),
   OOF-прогнози, зважене image-level злиття. Інакше 2D-CNN на одному
   спліті й ML на іншому порівнювати не можна.
8. **Вхід і нормалізація перевіряються окремо від моделі** — Група 0
   (ablation представлень) і тест train-у-режимі-inference. Обидва
   дефекти, знайдені так, коштували 0.1135 замість 0.9187 і хибного
   висновку про ієрархію методів.

## Розширене порівняння моделей

`src/train_ml_models.py` `train_and_compare()` підтримує три режими
понад базові 6 моделей:

- **XGBoost** (`use_xgboost=True`, авто, якщо встановлений) — 7-ма
  базова модель, сучасний градієнтний бустинг.
- **Voting (soft) + Stacking** (`use_ensembles=True`) — ансамблі
  будуються з top-3 базових моделей за `f1_macro`. Stacking
  використовує `LogisticRegression` як фінальний оцінювач.
- **GridSearchCV для top-k** (`tune_top_k=2`) — підбір
  гіперпараметрів через `GridSearchCV` з `GroupKFold(n=3)` за
  `source_image`. Тюнені моделі додаються у таблицю порівняння як
  `<name>_tuned`, найкращі параметри зберігаються в
  `model_comparison.csv` колонка `best_params`.

У веб-інтерфейсі (`/training`) усі три режими виносяться окремими
чекбоксами; у таблиці результатів кожен рядок має тип:
`base` / `tuned` / `ensemble`.

Програмно:

```python
from src.train_ml_models import train_and_compare

res = train_and_compare(
    use_xgboost=True,
    use_ensembles=True,
    tune_top_k=2,
)
```

Сітки гіперпараметрів задані у `PARAM_GRIDS` (тому ж файлі) — їх
можна звузити чи розширити під свої експерименти.

## Спектральні (FFT) ознаки

`src/feature_extraction.py` додає до 19 часо-просторових ознак ще
9 спектральних (через `scipy.fft.rfft`):

- `fft_centroid` — спектральний центроїд (середня частота за енергією);
- `fft_bandwidth` — спектральна ширина;
- `fft_rolloff` — частота, нижче якої 85% енергії;
- `fft_ratio_low / mid / high` — частки енергії в трьох смугах;
- `fft_peak_freq`, `fft_peak_mag` — частота і амплітуда головного спектрального піка;
- `fft_flatness` — Wiener entropy (тон vs шум).

Ці ознаки часто допомагають розрізняти схожі органічні сполуки
(наприклад acetone vs ethanol), де часові ознаки сильно перетинаються.

## Signal augmentation

`src/signal_augmentation.py` + параметр `augment_factor` у
`build_dataset()` дозволяють згенерувати N додаткових копій
кожного валідного імпульсу з:

- гауссовим шумом ~3% від std;
- амплітудним скейлом у [0.90; 1.10];
- циклічним часовим зсувом до ±4% довжини;
- (з ймовірністю 50%) невеликим time-warp.

Аугментовані рядки помічаються `is_augmented=True` у CSV.
**Важливо**: `source_image` зберігається тим самим, тому
`GroupShuffleSplit` гарантує, що оригінал та його аугментовані копії
не потрапляють одночасно в train і test.

**Train-only augmentation policy.** Після group-split і `train_ml_models.py`,
і `evaluate.py` додатково фільтрують `test_idx`, залишаючи лише рядки
з `is_augmented=False`. Тобто:

- **Train** отримує усі дані (оригінали + аугментовані копії) → більше зразків для навчання.
- **Test** містить виключно реальні (неаугментовані) приклади → метрики чесні щодо справжніх сенсорних даних, а не синтетично спотворених копій.

Це стандартна практика наукових публікацій з augmentation.

У веб-інтерфейсі параметр `augment_factor` виставляється на сторінці
`/pipeline` (число копій на імпульс, 0 = вимкнено). Рекомендований
діапазон 2–3.

## Ансамблі: як виправлено Stacking

Початкова версія Stacking використовувала тільки top-3 базові моделі —
вони часто корельовані (RF + GBM + XGB) і дають однакові помилки, що
позбавляє ансамбль сенсу. Виправлено:

- Базові — **усі** доступні моделі (різноманітність помилок);
- `passthrough=True` — фінальна `LogisticRegression` бачить і вихідні
  ознаки, не лише ймовірності base-моделей;
- `cv=5` (адаптивно зменшується, якщо мало груп);
- `n_jobs=1` для StackingClassifier — уникаємо вкладеного паралелізму
  з `n_jobs=-1` всередині base-моделей.

Voting (soft) залишається на top-3 — його сенс саме в усередненні
найкращих, не в різноманітності.
